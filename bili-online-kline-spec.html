B站直播「高能用户数」K线采集系统
—— 自包含实现规格书

把直播间的实时热度做成一张合格的 K 线图：高能用户数 OHLC 蜡烛主图 + 弹幕量 / 礼物电池两条量能副图。本文写给零上下文的实现者（另一台机器上的 agent 或工程师）——所有领域知识、接口口径、实测证据均内联在文内，不依赖任何外部私有上下文。

§0任务卡（TL;DR）

做什么：为 B 站直播间（默认 7777，德云色）自建一份「高能用户数」时间序列数据集：一个常驻采集进程双通道写入 SQLite；一个出图脚本聚合出 1m / 1h / 1d 三档 OHLC，渲染成主图 K 线 + 双量能副图的静态 HTML。

给实现者的话 —— 本文档的使用契约

① 本文自包含：不要假设你能访问本文之外的任何上下文（原始对话、私有笔记、原机文件）。

② 所有标 实测 的数据是 2026-08-12 的快照证据；接口行为可能漂移，动手前先跑 §2.2 的探活命令重新验证，与本文不符时以你的实测为准，并在实现记录里标注差异。

③ 口径出处分级：实测 当日验证过 · 推断 合理推测未验证 · 社区共识 开发者社区逆向结论 · 通识 平台公开常识。写代码时可信赖前者，对后两者保留验证心。

硬约束

  • 必须 只读采集：不发弹幕、不点赞、不触发任何互动接口。
  • 必须 单 Python 进程（asyncio 双协程），SQLite 单库，无外部服务依赖。
  • 必须 默认不存弹幕全文，只存分钟计数（§4.2）。
  • 必须 遵守 §2.4 风控与礼貌规则（频率上限、退避、必带 header）。
  • 建议 预留多房间扩展（所有表带 room_id），v1 只跑一个房间。

验收以 §8 清单为准。历史数据不可回溯，数据从进程首次启动起积累（T+0 起点）：当天可看分钟 K，一周后小时 K 成型，日 K 需积累一至两个月。

§1背景与目标

B 站直播间右上角的「高能用户数」是一个实时波动的量（观众进来涨、离开跌），天然适合做 OHLC 蜡烛聚合——就像股价。但 B 站没有任何公开接口提供它的历史序列，第三方数据站（danmakus.com、laplace.live）只收录 Vtuber，不覆盖游戏区主播 实测。所以：想要这张 K 线图，唯一的路是自己长期采集。

目标图（合格线 = 结构对齐主流行情软件）：

LAYOUT
┌──────────────────────────────────────────┐
│ 主图  高能用户数 OHLC 蜡烛（1m/1h/1d 切换）│
├──────────────────────────────────────────┤
│ 副图① 弹幕量柱形，每分钟条数    ← “成交量” │
├──────────────────────────────────────────┤
│ 副图② 礼物电池柱形，每分钟电池  ← “成交额” │
└──────────────────────────────────────────┘
  三块共享时间轴，缩放/十字线联动（§6.3 验收）
  • 主图标的是高能用户数而非「人气值」——人气值是加权热度，量纲含水；高能数≈真实在线登录观众（§2.1）。
  • 弹幕量是活跃度「成交量」；礼物电池是真金白银「成交额」；弹幕数/高能数 = 人均活跃度，高潮时刻一眼可见。

2.1概念与口径

高能用户数
onlineNum		本系统的 K 线标的。≈ 当前在直播间内的已登录观众数（游客不计），实时口径、随进出增减。证据：读数会下降（6190→6091）；6190 人中有积分上榜者仅 ~150 人，故「互动过才算」不成立（详见 §A）。实测
人气值 online加权热度值，量纲不是人数（同场读数 39.9 万 vs 高能 6190）。只做参考列，不做标的。实测
高能榜 score榜单上每人的分 = 本场累计互动积分：送礼按电池计大分；进场/停留/点赞类计 1~2 小分（小分构成无官方定义）。累计量只涨不跌，不适合做 K 线，但 top1 分与榜和可快照留档画「收入进度」。每场开播重置。实测 + 推断
电池 / 金瓜子充值换算：1 元 = 10 电池 = 1000 金瓜子，即 1 电池 = 100 金瓜子。礼物事件里的 total_coin 单位是金瓜子（§2.3）。免费礼物走「银瓜子」，不计钱。通识
SC / 醒目留言付费置顶留言（SuperChat），price 字段单位是元。通识
大航海 guard_level包月贵族：1=总督、2=提督、3=舰长、0=无。跨场持续，非本场量。通识
live_status0=未开播，1=直播中，2=轮播（放录像）。只有 =1 的时段进 K 线。社区共识
「N人看过」watched_show本场累计进场 UV（只涨不跌）。想要但拿不到——所在接口有风控（§2.2-F），v1 放弃。实测

2.3WebSocket 弹幕通道（弹幕/礼物计数唯一可靠源）

B 站弹幕 ws 协议：先调 getDanmuInfo 拿 token 和 wss 主机表 → 连 wss://<host>/sub → 发认证包 → 每 30s 心跳 → 收压缩二进制消息帧。建议 不要手写协议，直接用 blivedm（Python asyncio 库，处理握手/心跳/解压/重连全流程；安装方式以其 README 当前说明为准，pip 包名 blivedm，若 PyPI 版本陈旧则 pip install git+https://github.com/xfgryujk/blivedm）。

需要监听的事件（blivedm 回调名以其当前版本为准，事件 cmd 名是稳定的）：

事件 cmd计数逻辑出处
DANMU_MSG弹幕一条 → danmaku_cnt += 1。匿名连接下发送者用户名会被打码（uname="***"），不影响计数。社区共识
SEND_GIFTgift_cnt += num；若 coin_type == "gold"：gift_battery += total_coin / 100（total_coin 单位金瓜子，÷100 = 电池）。coin_type == "silver" 是免费礼物，只计条数不计电池。社区共识
SUPER_CHAT_MESSAGEsc_cnt += 1；sc_rmb += price（price 单位元）。社区共识
ONLINE_RANK_COUNT服务端推送的高能数变化。v1 不用它做主图（推送时机不受控，不如 15s 均匀轮询规整），可 DEBUG 日志留档做对照。社区共识
匿名连接的现实与退路（按顺序尝试）

现状：2023 年起 B 站对未登录 ws 连接收紧——用户名打码（计数无损）；getDanmuInfo 匿名调用可能被风控拒。推断，装机时验证。

退路①：先 GET https://www.bilibili.com/ 种 buvid3 cookie 再握手（blivedm 传入 aiohttp session 即可）。

退路②：从浏览器手动导出 SESSDATA cookie，经环境变量注入（必须 不硬编码、不进 git、不进日志）。只读采集场景风险低。

退路③（有损兜底）：ws 彻底不通才退回 gethistory 每 5s 轮询、按 (ts,uid,text) 去重估算弹幕数，明知漏计、在数据里如实标 ws_ok=0。基本走不到这步。

2.4风控与礼貌规则

  • 必须 全部请求带 §2.2 的 UA + Referer；超时 10s。
  • 必须 轮询频率上限：直播中 15s/次，未开播 60s/次（§5.2）；单 IP 单房间。这与网页端自身轮询同量级，属正常访问形态。
  • 必须 失败指数退避：5s 起，×2 递增，封顶 5min；连续失败 20 次 → 进程以非零码退出（交给守护器拉起并留下告警日志行，见 §5.4 快速失败）。
  • 必须 收到 code=-352（风控）：轮询间隔立即降为 60s，并重种 buvid3；持续 30min 仍 -352 → 快速失败退出。
  • 必须 纯只读：整个系统不调用任何写接口（不发弹幕/不点赞/不关注）。
  • 建议 尊重目标：这是公开页面数据的低频礼貌采集，等价于挂一个网页观众；不要因为"想要更细的 K 线"把间隔压到秒级。

§3系统架构

双通道单进程：轮询管主图，ws 管副图。轮询给 OHLC 提供均匀采样（比事件推送规整），且 ws 断线不牵连主图数据。

  • 为什么不全走 ws？ONLINE_RANK_COUNT 推送时机不受控（人多时秒级多条、人少时长时间不推），OHLC 需要均匀采样；且轮询无连接状态，天然抗断线。
  • 为什么不全走轮询？弹幕 REST 接口只留 10 条（§2.2-C），计数必须吃事件流。
  • 两协程共享一个 SQLite 连接串行写（或各自持连接，WAL 下单写者多读者安全；建议 用一个 asyncio 队列汇到单写协程，最省心）。

§4数据设计

4.1DDL（全文照抄）

SQL
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;

-- 15s 一行：K线主图数据源（轮询通道写入）
CREATE TABLE IF NOT EXISTS samples (
  ts          INTEGER NOT NULL,   -- Unix epoch 秒，UTC
  room_id     INTEGER NOT NULL,   -- 真实房号（545068）
  online_num  INTEGER,            -- 高能用户数 ← K线标的
  popularity  INTEGER,            -- 人气值（参考列）
  rank_total  INTEGER,            -- 榜单可见 score 之和（收入进度，可空）
  top1_score  INTEGER,            -- 榜一分数（可空）
  live_status INTEGER             -- 0未播 1直播 2轮播
);
CREATE INDEX IF NOT EXISTS idx_samples_room_ts ON samples(room_id, ts);

-- 每分钟一行：量能副图数据源（ws 通道分钟桶落盘）
CREATE TABLE IF NOT EXISTS minute_stats (
  minute_ts    INTEGER NOT NULL,  -- 分钟对齐 epoch：ts - ts%60
  room_id      INTEGER NOT NULL,
  danmaku_cnt  INTEGER DEFAULT 0, -- 弹幕条数 ← 副图①
  gift_cnt     INTEGER DEFAULT 0, -- 礼物条数（含免费）
  gift_battery INTEGER DEFAULT 0, -- 付费礼物电池数 ← 副图②
  sc_cnt       INTEGER DEFAULT 0, -- SC 条数
  sc_rmb       INTEGER DEFAULT 0, -- SC 金额（元）
  ws_ok        INTEGER DEFAULT 1, -- 该分钟 ws 是否在线（0=断线，图上灰柱）
  PRIMARY KEY (room_id, minute_ts)
);
  • 时间一律存 UTC epoch 秒；聚合/展示时 +8h 转北京时间，日 K 日界 = 北京时间自然日（§6.1）。
  • 必须 不建预聚合表——两百万行读时聚合毫秒级，物化是过度设计；真慢了再加也不迟。
  • minute_stats 用 INSERT ... ON CONFLICT(room_id,minute_ts) DO UPDATE 累加，天然幂等（进程重启同一分钟不丢不重）。

4.2数据量（SQLite 可行性论证）

表写入节奏行/年体积/年（估）
samples15s×24h（未播时 60s，此处按上限估）≤ 210 万50~100MB 含索引
minute_stats每分钟 1 行（日播 12h 计）~26 万<10MB
合计—~236 万约百 MB

SQLite 舒适区在千万~亿行量级，本系统十年不用换库。工况是「单写者（daemon）+ 偶发读者（出图脚本）」，WAL 模式下互不阻塞，正是 SQLite 的最佳场景。若 v2 打开弹幕全文存储（约 +1.8GB/年）依然可行。

5.2参考实现骨架

诚实声明

下列骨架未经运行验证（本规格在无 Python 运行环境下编写），控制流和口径是规范性的 必须，具体 API 签名（尤其 blivedm 回调名）以库当前版本 README 为准。

PYTHON · tracker.py 骨架
# deps: python>=3.10, aiohttp, blivedm  (pip install aiohttp blivedm)
import asyncio, aiohttp, sqlite3, json, time, os, signal, logging
from logging.handlers import RotatingFileHandler
import blivedm

UA = {"User-Agent": "Mozilla/5.0 ...", "Referer": "https://live.bilibili.com/"}
API_INFO = "https://api.live.bilibili.com/room/v1/Room/get_info"
API_RANK = "https://api.live.bilibili.com/xlive/general-interface/v1/rank/getOnlineGoldRank"

class MinuteBucket:                       # ws 事件的内存分钟桶
    def __init__(self): self.reset(0)
    def reset(self, m): self.minute=m; self.dm=0; self.gift=0; self.bat=0; self.sc=0; self.rmb=0
    def flush(self, db, room, ws_ok):     # 幂等落盘（ON CONFLICT 累加）
        if self.minute == 0: return
        db.execute("""INSERT INTO minute_stats VALUES (?,?,?,?,?,?,?,?)
          ON CONFLICT(room_id,minute_ts) DO UPDATE SET
          danmaku_cnt=danmaku_cnt+excluded.danmaku_cnt, gift_cnt=gift_cnt+excluded.gift_cnt,
          gift_battery=gift_battery+excluded.gift_battery, sc_cnt=sc_cnt+excluded.sc_cnt,
          sc_rmb=sc_rmb+excluded.sc_rmb, ws_ok=min(ws_ok,excluded.ws_ok)""",
          (self.minute, room, self.dm, self.gift, self.bat, self.sc, self.rmb, ws_ok))
        db.commit()

async def poll_loop(sess, db, room, ruid, cfg, state):
    backoff, fails = 5, 0
    while True:
        try:
            async with sess.get(API_RANK, params={"ruid":ruid,"roomId":room,"page":1,"pageSize":50},
                                headers=UA, timeout=aiohttp.ClientTimeout(total=10)) as r:
                j = await r.json()
            if j["code"] == -352:                 # 风控：降频 + 记录（§2.4）
                state["risk"] = time.time(); logging.warning("-352 risk control")
                await asyncio.sleep(60); continue
            items = j["data"]["OnlineRankItem"] or []
            db.execute("INSERT INTO samples VALUES (?,?,?,?,?,?,?)",
                (int(time.time()), room, j["data"]["onlineNum"], state.get("pop"),
                 sum(i["score"] for i in items), items[0]["score"] if items else None,
                 state.get("live", 0)))
            db.commit(); backoff, fails = 5, 0
        except Exception as e:
            fails += 1; logging.warning(f"poll fail #{fails}: {e}")
            if fails >= 20: logging.error("fast-fail: 20 consecutive"); os._exit(1)   # §5.4
            await asyncio.sleep(min(backoff, 300)); backoff *= 2; continue
        await asyncio.sleep(cfg["poll_live_sec"] if state.get("live")==1 else cfg["poll_idle_sec"])

# status_loop：每 60s GET get_info → state["live"], state["pop"]（结构同上，略）
# danmaku_loop：blivedm 客户端，回调里给 MinuteBucket 累加；
#   每逢分钟边界（int(t//60)*60 变化）flush 上一桶；断线期间 flush 时 ws_ok=0；
#   blivedm 自带重连；SIGTERM 时 flush 当前桶再退出（优雅收尾）。
# heartbeat_loop：每 cfg[heartbeat_min] 分钟 log 一行计数汇总（§5.4 进度日志）。

async def main():
    cfg = json.load(open("config.json"))
    # 启动：GET get_info 解析 短号→真实 room_id + ruid（§2.2-A），建表（§4.1 DDL）

5.3规范性要点（实现必须满足）

  • 必须 启动时解析短号（§2.2-A），失败重试 3 次后退出；真实 room_id / ruid 缓存在内存。
  • 必须 分钟桶按 minute_ts = ts - ts % 60 对齐；分钟边界与进程退出（SIGTERM/SIGINT）时 flush；落盘用 ON CONFLICT 累加保幂等。
  • 必须 ws 断线期间对应分钟记 ws_ok=0（图上显示灰柱缺口，不造假补数）；blivedm 重连后恢复 1。
  • 必须 未开播（live_status≠1）时轮询降为 60s；ws 保持连接（停播弹幕也照计）。
  • 建议 日志用 RotatingFileHandler（10MB×3 份），跨平台省掉 logrotate 依赖。

5.4长任务心跳三件套

  • 进度日志：每 5min 一行心跳 HB live=1 online=6190 dm/min=214 bat/min=350 ws=ok——沉默的 daemon 无法诊断。
  • 分段落盘：samples 逐条 commit、minute 桶逐分钟 flush（WAL 下开销可忽略）；任何时刻 kill 掉最多丢当前分钟。
  • 快速失败：连续 20 次轮询失败或 -352 持续 30min → 非零码退出 + ERROR 日志行，交给守护器重启，绝不静默挂死空转。

6.1聚合：pandas 一行出三档

PYTHON
import pandas as pd, sqlite3
cx = sqlite3.connect("data/bili_online.db")

df = pd.read_sql("SELECT ts, online_num FROM samples WHERE room_id=? AND live_status=1",
                 cx, params=(545068,))
df.index = pd.to_datetime(df.ts, unit="s") + pd.Timedelta(hours=8)   # 北京时间，日界随之正确
k1m = df.online_num.resample("1min").ohlc().dropna()                # 1h→"1h"，1d→"1D"

vol = pd.read_sql("SELECT * FROM minute_stats WHERE room_id=?", cx, params=(545068,))
vol.index = pd.to_datetime(vol.minute_ts, unit="s") + pd.Timedelta(hours=8)
# 1h/1d 档：danmaku_cnt/gift_battery 用 .resample("1h").sum()；ws_ok 用 .min()（有断线即标灰）

  • 必须 弹幕/礼物副图与主图对齐到同一时间桶；1m 档直接用 minute_stats 行。
  • 建议 输出三档数据内嵌进 HTML（JSON 变量），默认视图 = 近 7 天的 1m 档。
