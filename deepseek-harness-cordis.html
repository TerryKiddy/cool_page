Section 01 · 结论先行

30 秒版本

如果你只想知道"这东西值不值得看"，看这四条就够了。

1

DeepSeek Harness（命令行叫 dsh）是 DeepSeek 官方开源的 agent harness，功能位面上对标 Claude Code / Codex：能读写文件、跑命令、派子 agent、维护 plan，自带 Web UI（默认 127.0.0.1:3080）。2026-08-13 发的 v0.1 developer preview，MIT。

2

它的设计只有一句话：一切皆插件。模型适配器、工具注册表、会话日志、系统提示词组装、沙箱、存储、UI——包括 agent 主循环自己——全都是挂在同一棵树上的插件。官方文档的原话是："没有一个特权的 core 可以打补丁"，扩展 dsh 的方式是在旁边再挂一个插件。

3

Cordis 是让这句话成立的那层框架，而且它不是 DeepSeek 造的。Cordis 来自开源社区 cordiverse（MIT，自称"时空可组合性元框架"），DeepSeek 把它连同 8 个配套包一起 vendor 进仓库、改名到 @deepseek-ai/* 域下，并记录了 18 处本地修改。它背后有一篇 2026-08-13 的论文草稿。

4

一句话记住分工：Harness 是产品，Cordis 是"这个产品可以被整块换掉"的原因。换掉 ctx.shell 的 provider，Bash / PTY / LSP 一起搬到远程沙箱；换掉 subagent provider，你的子 agent 可以直接是 Claude Code 或 Codex——仓库里真有 subagent-claude-code 和 subagent-codex 两个包。

这页的证据标准

下面所有代码、事件名、状态机、包名，都来自 deepseek-ai/deepseek-harness 仓库 master 分支的官方文档原文（docs/architecture.md、docs/cordis-primer.md、七章 cordis-tutorial/、vendor/README.md 及自动生成的能力图）。属于我个人判断的段落会明确标出。

Section 02 · Cordis 的全部

五个概念，讲完这框架

官方 primer 用五句话概括了 Cordis。这五句话是理解整个 harness 的钥匙——后面所有复杂度都是它们的组合。

01 / Plugin

插件就是一个函数

不需要继承、不需要注册宏。导出一个 apply(ctx) 就是插件。框架加载时调用它，传进去一个 context——这个 ctx 是插件对外的唯一接口。

02 / Context

Context 是服务仓库

一个服务占住一个稳定的 ctx.<key>，比如 ctx.tools、ctx.llm、ctx.sessions。别的插件按 key 找它，而不是 import 某个具体实现——这就是配置能换掉实现的原因。

03 / inject

依赖用 inject 声明

export const inject = ['tools']。列出的服务不存在时，插件停在 PENDING 不动；一旦齐了才跑 apply。加载顺序由依赖决定，不由配置文件里的行号决定——把 YAML 里两行对调，输出一模一样。

04 / Events

类型化事件

服务通过 TS 声明合并注册事件名，再用 emit / waterfall / parallel / serial / bail 五种模式派发。用哪种模式是事件公开契约的一部分，新事件必须用 @mode 标注。

05 / Effects

所有注册都是可撤销的副作用

提示词片段、工具 schema、模型适配器、事件监听——全部通过 ctx.effect() 或 ctx.on() 安装，插件卸载时框架按逆序把它们全部撤回。你几乎不用手写 ctx.effect()，因为 ctx.on()、ctx.plugin()、ctx.tools.register() 本身就已经是 effect 了。这条是整套设计的地基，第 3 节展开。

hello.ts — 最小插件
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'          // 可选，只用于诊断显示

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}

文件里没有任何框架 bootstrap 代码。插件只描述"我贡献什么"，谁跟谁组装由 cordis.yml 决定。

greeter.ts — 占住 ctx.greeter
import { Service, type Context } from '@deepseek-ai/cordis'

// 编译期：把 greeter 加进 Context 接口，让 ctx.greeter 到处都有类型
declare module '@deepseek-ai/cordis' {
  interface Context {
    greeter: GreeterService
  }
}

export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')   // 运行期：注册成 ctx.greeter，这本身是个 effect
  }

  greet(who: string) {
    return `Hello, ${who}!`
  }
}

export const name = 'greeter'
export function apply(ctx: Context) {
  ctx.plugin(GreeterService)   // Service 子类本身就是插件
}

两半配合：super(ctx,'greeter') 管运行期，declare module 管类型。少了后者服务照跑，只是消费方失去类型安全。

consumer.ts — 按 key 拿，不 import 实现
import type { Context } from '@deepseek-ai/cordis'

export const name = 'consumer'
export const inject = ['greeter']   // 硬依赖：没有它就不加载

export function apply(ctx: Context) {
  // 能进到这里，ctx.greeter 一定就绪
  console.log(ctx.greeter.greet('world'))
}

// 软依赖写法：不 inject，用的时候探一下
// const greeter = ctx.get('greeter')
// console.log(greeter?.greet('maybe') ?? 'no greeter available')
cordis.yml — 应用就是一份清单
- name: './greeter.ts'
- name: './consumer.ts'

# 两行对调，输出完全一样 —— 顺序来自 inject，不来自行号
# 删掉 greeter.ts：consumer 停在 PENDING，不打印、不崩溃

Section 03 · 核心洞察

"时空可组合性"到底在说什么

Cordis 自称 a meta-framework of spatiotemporal composability，配套论文《A Programming Paradigm for Spatiotemporal Composability》（2026-08-13 草稿）。名字听着玄，拆开只有两件事，而且都很具体。

Temporal · 时间维度

组件被移除时，副作用能被完整回滚

论文的说法是 revertible effects：每一次对 context 的改动都自带一个逆操作，由运行时追踪。落到代码上就是——你注册的东西，框架替你记着怎么撤。

ctx.effect() 是唯一的手写形态
ctx.effect(() => {
  const timer = setInterval(tick, 200)
  return () => clearInterval(timer)  // ← 逆操作
})

但你很少写它，因为这些本来就是 effect：ctx.on()、ctx.plugin()、ctx.tools.register()、ctx.llm.registerAdapter()。卸载时它们自动解绑，永远不需要写 removeListener。

Spatial · 空间维度

依赖能被声明，并且是响应式的

论文叫 reactive coeffects：context 每次变化都会按组件的 coeffect 声明去通知它。落到代码上就是 inject，而且它不是一次性的启动检查。

关键行为

运行中某个被 inject 的服务消失了（provider 被卸载或热替换），所有依赖它的插件会跟着卸载；服务回来时再自动装回去。

这条防住了一类经典 bug：一个还在跑的消费者，手里攥着一个已经失效的服务引用。它自己的注册会随着依赖消失一起被撤掉。

=

两条合起来，才换来这三件事：① 改一行 cordis.yml 就能换掉实现，而不是重启进程；② HMR 保存文件就热替换，旧实例的注册不会残留；③ 卸掉 dsh-bash-local、挂上另一个 shell provider，所有 inject('shell') 的插件干净地对着新实现重启一遍。

我的判断（非官方口径）

"agent harness 需要一套插件框架"这个论断不新鲜，新鲜的是他们把可撤销性当成形式化目标去做，而不是当成最佳实践去劝。多数插件系统的卸载是"尽力而为"，于是没人敢真的在生产里热卸载。Cordis 把 revert 做成运行时义务，HMR 和"配置即架构"才敢当成日常功能用。

Section 04 · 交互

Fiber：一个插件实例的一生

每个被加载的插件实例拥有一个 fiber——它的运行时句柄和生命周期。理解这张状态机，就能解释 90% 的"我的插件为什么没反应"。点下面的按钮亲手跑一遍。

陷阱 #1

PENDING 是静默的

插件 inject 了一个没人提供的服务，它永远等下去，不报错、不打印——因为 provider 完全可能稍后才挂上。官方 tutorial 直说这是"我的插件为什么什么都没打印"的常见答案。

怎么查

遍历 registry

任何 context 都能枚举插件注册表：

for (const rt of ctx.registry.values())
  for (const f of rt.fibers)
    if (f.state === FiberState.PENDING)
      report(f.name)
陷阱 #2

异步 disposer 是并发的

卸载时 disposer 按注册的逆序开始跑，但多个 async disposer 是并发的，没有串行完成保证。顺序敏感的清理必须塞进同一个 ctx.effect() 里 await。

Section 05 · 交互

五种派发模式，和那个会咬人的 waterfall

服务负责"直接调用"，事件负责"我宣布一件事，不关心谁在听"。派发模式决定了监听者能不能返回值、能不能并发、能不能截断别人。

模式调用语义
emitctx.emit(name, ...args)同步广播。返回的 promise 和值既不 await 也不收集。纯观察用。
parallelawait ctx.parallel(...)所有监听者并发跑，一起 await。
serialawait ctx.serial(...)按注册顺序串行 await；第一个返回非 null/false/undefined 的胜出并终止其余。
bailctx.bail(...)serial 的同步版本。
waterfallctx.waterfall(name, ...args, next)环绕式中间件。监听者收到 (...args, next)：调 next() 把（可能被包装过的）结果交给下一个；不调就地短路。整套拦截能力都建在它上面。

waterfall 现场演示

两个监听者：第一个把下游结果转大写，第二个在输入里含 blocked 时直接返回、不调 next()。看输入不同时链条怎么走。

仓库级的铁律

只观察或只加注解的 waterfall 监听者，必须调 next()。不调 = 你在主动短路。在一个日志监听里忘了 next()，会静默地把默认行为对所有下游吞掉。官方 primer 把这条列为 standing rule。这也是"环绕式中间件"这个模型的固有税：能力越大，忘一行的代价越大。

harness 里真正用 waterfall 的地方：agent/pre-step（决定模型看见什么）、agent/request（插件可以替换模型调用配置）、llm/stream、tools/pre-execute / tools/execute / tools/post-execute、approval/request（策略可以代替人回答审批）。

Section 06 · 从框架到产品

一个跑起来的 dsh，是怎么被"叠"出来的

Cordis 只给了机制，Harness 需要一套发行格式。它的答案是三层叠加：bundle → profile → patch，最后得到一棵插件树。

Bundle

一沓配置行 + 代码

dsh-base 是每个 profile 的第一层：模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测。dsh-web-app 加浏览器应用，dsh-headless 加一个完全无服务器的一次性 runner。

Profile

一份具名组合

存在 Harness home 里，列出它要叠哪些 bundle、装了哪些树外插件、以及用户自己的 cordis.patch.yml。web 和 headless 作为模板出厂。

Patch

按 id 精确改写

补丁按 id 命中某一行、整体替换它的 config，或插入新行。叠加顺序：各 bundle → profile 的 patch → home 级 patch → --patch 覆盖层。

Section 07 · 最有用的一个概念

Capability Seam：换一个 provider，整个产品跟着变

Harness 把"可替换能力"定义成一个有三个角色的结构，叫 seam（接缝）。文档说得很硬：三个角色齐了才叫 seam，单独一个角色不是；新增一项能力意味着把三个角色都设计出来。

Role 1 — Service Definition

拥有 ctx.<key> 和词汇表类型的那个 Cordis Service。可以是抽象类，也可以是具体注册表，但绝不能是一个 TS interface。

dsh-shell
Role 2 — Service Provider

一个或多个实现。它们互相之间不需要知道对方存在，配置选谁就是谁。

dsh-bash-local
dsh-bash-sandbox
Role 3 — Consumer

inject 这个服务去用的人，常见是一个面向模型的工具。

dsh-tool-bash

一次替换，搬走三样东西

Section 08 · 主循环

一个 turn 里到底发生了什么

术语先对齐：step = 一次模型请求 + 它调起的那些工具。turn = 零个或多个 step；它在第一份输入被认领之前开启，在"什么都不欠了"之后关闭。零个 step 的 turn 也是合法的——被拒绝的输入照样留下一条 turn 记录。

turn/start 认领 next-step 输入 + 一条排队消息 组装提示词片段 + 工具 schema → agent/pre-step waterfall · reject | enter(messages) 被拒绝，或第一次 enter 被改写成空 → 关掉 turn，不花 step step/start 把 enter 进来的消息作为 user/message 落日志 从日志推导模型历史 agent/request → llm/stream → assistant/chunk* → assistant/message tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* step/end 工具还欠一次请求，或新的 next-step 输入到了 → 认领 → 下一个 step → agent/turn-stopping serial · 没有 next() turn/end
持久会话事件（可回放） waterfall 扩展点（必须调 next） 其他活体扩展点
三个事件域

选错域是最常见的设计错误

  • Session 事件——追加进日志的持久事实，经 session/event 广播。当这件事必须活过一次重载时用它。
  • Agent 事件（agent/*）——携带一个活的 Agent：收件箱、step、状态、请求、校验、续跑。用来观察或拦截正在飞的工作。
  • Capability 事件（fs/*、tools/*、telemetry/*）——把策略和适配器挂到接缝上，不用 import 主循环。
硬不变式

"模型可见 = 已落日志"

任何进到模型请求里的东西，都必须能从会话日志重建出来，而且有一条运行时不变式在断言这件事。

推论很硬：想给模型加一种新的可见输入，就必须新增一个会话事件——扩展 SessionEventMap，然后从日志渲染。fork、resume、转写、遥测、持久化全部由这一条流派生。

我的判断（非官方口径）

这条不变式是这个仓库里我最看重的设计。一旦"模型看见的"和"日志记下的"允许分叉，会话回放、上下文压缩、fork、审计就会全部变成近似值。它把这层做成运行时断言，代价是加一种上下文注入必须走一遍事件类型扩展——用开发便利换取可回放性。对一个要长期做上下文工程的 harness，这笔交易划算。

Section 09 · 动手

五分钟：跑起来，然后写个工具

最快路径 · 需要 Node.js
$ npx @deepseek-ai/dsh web
# Web UI 默认在 http://127.0.0.1:3080

# 从源码跑：
$ git clone https://github.com/deepseek-ai/deepseek-harness.git
$ cd deepseek-harness && pnpm install && pnpm run build
$ pnpm dsh web

首次进去要做两件事：Settings → Models 填 API key（存完立即生效，不用重启）；然后 Choose workspace 选一个工作目录——没选之前会话输入框是不可用的。官方还给了四种运行形态：Standard（完整 coding agent）、Code（加 Code Mode SDK 的多步 TypeScript 编排）、Minimal（只有 bash + 字符串替换编辑器）、Creator（做自定义预设、运行时内省和插件实验）。

greet-tool.ts
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'
import { CallId } from '@deepseek-ai/dsh-llm'

export const name = 'greet-tool'
export const inject = ['tools']        // 等工具注册表就绪

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet the named person.',
    parameters: {
      name: { type: 'string', required: true, description: 'Who to greet' },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }))

  // 手动驱动一次真实执行流水线，替模型走一遍
  void (async () => {
    const result = await ctx.tools.execute({
      callId: CallId('demo-1'),
      name: 'greet',
      arguments: { name: 'Cordis' },
      signal: new AbortController().signal,
    })
    console.log('tool replied:', JSON.stringify(result.content))
  })()
}

ctx.tools.register() 把 disposer 挂到调用它的插件上，插件卸载工具自动下架。defineTool 把 parameters 转成给模型看的 JSON Schema、推断 args 类型，并在 execute 之前校验模型给的参数。

tool-logger.ts — 完全不认识 greet-tool
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-tools'   // 只为拿到声明合并

export const name = 'tool-logger'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.on('tools/result', (exec, result) => {
    const text = result.content
      .map(b => (b.type === 'text' ? b.text : ''))
      .join('')
    console.log(`[tool-logger] ${exec.name} -> ${text}`)
  })
}

这就是整个架构的缩影：两个插件谁也不知道对方存在，注册表服务和事件把它们接起来。想给全仓所有工具加 timeout / 重试 / 埋点，也是同一个套路——挂 tools/execute waterfall，不碰任何工具的代码。

配置的两个坑

① 给每行写 id。没有 id 的条目每次读取都会拿到一个新生成的 id，于是任何一次改 cordis.yml，它都算"删除+新增"而重新挂载，哪怕它自己那几行一个字没动。

② 模块名拼错不会崩。解析不了的条目走 Cordis logger 服务上报，而启动早期这条报告可能在 console exporter 就位前就丢了。新加的条目"什么都没发生"，先查拼写。

Section 10 · 平衡看

它买到了什么，又付了什么

买到的

可替换性是真的，不是 PPT

  • 换 provider 不用 fork：文件系统 + 子进程一起指向远程沙箱，Bash / PTY / LSP 跟着走。
  • 子 agent 可以是 Claude Code、Codex、ACP 对端或进程内 fork——同一个接口。
  • HMR 敢在开发时天天用，因为卸载是有保证的而不是尽力而为。
  • 会话日志是唯一真相源，回放 / fork / 压缩 / 遥测全从它派生。
  • MIT，框架层连同上游 Cordis 一并 vendor 进仓库：可审计、可打补丁、版本钉死。
付掉的

灵活性的账单

  • PENDING 是静默的。依赖没满足 = 不报错、不打印，只是永远不启动。
  • 服务名是每应用一个扁平命名空间。harness 已经占了 tools、llm 这类通名，自定义服务必须加前缀。
  • waterfall 忘调 next() 会静默吞掉下游默认行为。这是能力换来的固有风险，只能靠纪律和 review。
  • 异步 disposer 并发执行，顺序敏感的清理必须自己塞进同一个 effect 里 await。
  • developer preview。README 用全大写写着：会有破坏兼容的变更。
