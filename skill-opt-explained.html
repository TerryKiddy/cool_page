01 · 先校准概念

“优化 Skill”其实有两道题

很多人把两者混在一起：skill 可能能力很强，却根本没被召回；也可能每次都触发，但执行结果并不比裸模型好。

PROBLEM / A

能力优化

给同一批真实任务，比较「有 skill」和「无 skill / 旧 skill」的输出。目标是提升正确性、稳定性与可复用性。

PROBLEM / B

触发优化

给一批该触发与不该触发的用户请求，检查 description 能否让系统正确召回。目标是少漏调，也少误调。

好 Skill = 正确触发 × 正确执行 × 可验证改进 任何一项接近 0，整体体验就会崩掉。
02 · 优化对象

先知道自己在改哪一层

一个 skill 不是单块提示词。它有三层加载结构，优化时要把问题放回正确的层。

03 · 两条优化回路

从直觉，走向受控实验

点击切换两条回路。它们共享“评测—改写—复测”的骨架，但数据和指标完全不同。

01

定义意图

说清楚做什么、何时触发、输出长什么样。

02

真实任务

准备 2–3 个真实 prompt，不用“玩具题”。

03

并排运行

同题对比新 skill 与无 skill / 旧版本。

04

人 + 指标

人看整体质量，断言检查可客观验证的要求。

05

归因改写

从失败轨迹归因，改写后完整重跑。

01

构造查询

约 20 条，正例与刁钻近邻负例各半。

02

人工复核

确认每条到底应该触发还是不应该。

03

训练 / 留出

60% 用来迭代，40% 留作最终检验。

04

重复采样

每条多跑几次，看触发率而非单次运气。

05

按测试集选

最佳版本由留出集决定，防止背答案。

为什么必须留出 40%？

如果你一边看全部题目，一边改 description，它很容易把这 20 道题“背下来”。留出集从不参与改写，才更接近未来真实请求。

06 · 进阶：反思式进化

GEPA 把手动循环变成候选进化

它把 SKILL.md 或提示词当成可进化 artifact：从失败轨迹反思，生成候选，小批筛选，再做完整验证。这里讲的是思路，不等同于所有 Skill Opt 工具都必须用 GEPA。

01 · SEED

建立基线

先知道当前版本在哪些题上失败。

02 · REFLECT

失败反思

基于轨迹提出有原因的具体改写。

03 · MINI

低成本筛选

先在小批任务上淘汰无效候选。

04 · FULL

完整验证

过门槛后才跑全量，防偶然提升。

05 · MERGE

组合优势

把不同专家候选的长处再次验证。

PARETO FRONT：候选 A 擅长准确率 候选 B 更省 token 候选 C 在边界任务更稳。不是只留“平均分最高”的一个。
07 · 你的第一轮实战

七步跑完一个最小闭环

点击每一行可以打勾。清单会保存在浏览器本地，下次打开仍在。

写一句明确的成功定义

不是“更专业”，而是“能识别全部事实主张，并为每条给出处”。

✓

准备 3 个真实任务

简单、典型、边界各一个；别只用你最熟悉的样例。

✓

冻结基线版本

新 skill 对比无 skill；改旧 skill 时，先快照旧版本。

✓

并排运行，不看标签先评

尽量盲评，避免“知道哪个是新版”影响判断。

✓

把失败归因到正确层

触发、正文、脚本、外部依赖，修复位置并不一样。

✓

删掉不产生价值的指令

更长不等于更强。重复工作应沉淀成脚本，而不是反复口述。

✓

完整重跑，防止局部回归

修好一个 case 可能破坏另一个；每轮都跑全套。

08 · 自测

你真的理解了吗？

四道题，不记术语，只检查你是否抓住实验逻辑。

QUESTION 01

skill 每次都能触发，但输出质量没有提升。先改哪里？

触发已经不是问题。应看执行轨迹，定位正文、脚本或知识资源的缺口。

QUESTION 02

为什么负例不能写成“请算斐波那契数列”？

高价值负例应共享关键词或相邻意图，却确实不该触发。

QUESTION 03

候选版通过率更高，但 token 是基线的 8 倍。正确结论是？

优化是多目标问题：质量、稳定性、成本、延迟都可能进入决策。

QUESTION 04

description 在训练集 100%，留出集 65%。最可能发生了什么？

训练高、测试低是典型过拟合信号。应扩大边界样本并做更能泛化的描述。

THE TAKEAWAY

别问“我改得更好吗？”
问“证据更强了吗？”

一份好 skill 的终点，不是措辞看起来更聪明，而是在新任务上更可靠地被召回，并以可接受的成本稳定完成工作。
