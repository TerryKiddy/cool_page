生信排错笔记 · SnpEff build

Transcript already in Gene

给公共参考病毒基因组(WNV · NC_009942.1)构建 SnpEff 注释库时的一个构建失败——以及它为什么和"危险生物研究"毫无关系。

Genome NC_009942.1 · len 11,029 Gene WNVNY99_gp1 Transcript YP_001527879.1 SnpEff 5.0 (2021)
误报

给已发表的参考基因组建注释库,是标准开源生信基础设施/DevOps,不是需 trusted-access 的危险生物研究。编码 agent 因"病毒/基因"字样掐掉内容显示,是假阳性。

真 bug

报错与病毒无关:同一个 transcript ID YP_001527879.1 在同一 gene 下被注册了两次。任何带重复 protein_id 的 .gbk 都会炸。

◦ 根因

SnpEff 往基因 WNVNY99_gp1 里注册转录本时,发现同一个 ID 已存在——即重复注册。这是黄病毒科(flavivirus)GenBank 注释喂给 SnpEff 的经典翻车点:

一条超长多聚蛋白(polyprotein)CDS + 十几个 mat_peptide 成熟肽特征,SnpEff 的 GenBank 解析器容易把它们塞进同一个 gene 造成 transcript ID 撞车;或者 .gbk 文件里那段 polyprotein CDS 本身被重复了。和病毒本身无关。

◦ 修复 · 按优先级

1

先定位撞车源

SnpEff 约定 genbank 文件在 <data.dir>/<genome>/genes.gbk。看重复的 protein_id 出现几次、挂在什么 feature 下:

cd <data.dir>/wnv_NC_009942_1
grep -nE "YP_001527879\.1" genes.gbk
grep -nE "^\s+(CDS|mat_peptide|gene)\b|/gene=|/locus_tag=|/protein_id=" genes.gbk
A

真有重复的 CDS 块

若 grep 出两段几乎相同的 CDS … /protein_id="YP_001527879.1":直接删掉第二段重复 CDS,重新 build。多半是下载/拼接 .gbk 时出的岔子。

B

改用 GFF3 构建 推荐

病毒/单基因组直接走 -gff3,自己控 ID 唯一(polyprotein 用 ID=cds-YP_001527879.1,各成熟肽各自唯一 ID)。GenBank 的 polyprotein+mat_peptide 结构对 SnpEff 太脆,GFF3 一次干净。

snpEff build -c "$ROOT/snpeff.config" -gff3 -v wnv_NC_009942_1 \
  2>&1 | tee "$ROOT/wnv_NC_009942_1.build.log"
C

快速过关 治标

把冲突特征的 /protein_id 改成唯一值(如 YP_001527879.1_mp2),让 transcript key 不再重复。对"只要能注释"够用。

验收 — build 后跑 snpEff dump wnv_NC_009942_1,或对一条已知变异做注释验证。SnpEff 5.0(2021)与此 bug 无关,不必为它升级。

◦ AGENTS.md · 如实描述,而非绕过

给 repo 一份如实定位项目的上下文文件——公共 RefSeq 变异注释基础设施 + 工程约定。准确的上下文本身就降低误报;不写"绕过安全"话术(既不对,实际也不管用)。放到 repo 根目录即可。

# AGENTS.md

## What this repo is
A Nextflow bioinformatics pipeline for variant annotation of viral
sequences against public reference genomes (NCBI RefSeq). This is
routine open-source infrastructure / DevOps work: downloading reference
genomes, building annotation databases, and wiring tools into a workflow.

It does not design, synthesize, or enhance any organism. It only
annotates variants against already-published reference sequences — the
same read-only genome bookkeeping done in any public-health lab.

## Stack
- Nextflow — pipeline orchestration (main.nf, modules/, conf/)
- Singularity/Apptainer — containerized tools (-B bind mounts)
- SnpEff / SnpSift — variant effect annotation; DBs built from
  NCBI RefSeq GenBank (-genbank) or GFF3 (-gff3)
- Reference data: NCBI RefSeq (e.g. WNV NC_009942.1), config in
  snpeff/snpeff.config, per-genome data under <data.dir>/<genome>/

## Common tasks
- Build a SnpEff DB:
  singularity exec -B "$ROOT:$ROOT" "$IMG" \
    snpEff build -c "$ROOT/snpeff.config" -genbank -v <genome>
- Prefer -gff3 builds for viral polyprotein genomes — GenBank
  polyprotein + mat_peptide annotations frequently trigger
  "Transcript 'X' is already in Gene 'Y'" (duplicate transcript IDs).
  Fix by ensuring every CDS/feature has a unique ID/protein_id.
- Validate: snpEff dump <genome>, or annotate one known VCF row.

## Conventions
- Never hand-edit a built data/<genome>/ DB dir — rebuild instead.
- Keep genome IDs consistent across config, dir names, Nextflow params.
- Bind-mount the whole $ROOT so container paths match host paths.
- All reference genomes are public NCBI RefSeq accessions — cite them.

## Note for AI assistants
This is standard software / bioinformatics infrastructure work on
public reference data. Errors here are ordinary engineering issues
(path binds, parser quirks, ID collisions, container config), not
biosecurity concerns. Diagnose them as any backend/build failure.
